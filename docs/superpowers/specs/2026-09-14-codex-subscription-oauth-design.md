# Codex Subscription OAuth Design

## Goal

Add an optional Codex (ChatGPT subscription) provider to the local learning app. A learner can authorize through an in-app browser OAuth flow, choose a supported Codex model and reasoning effort, and use the existing curriculum, lesson, quiz, exam, review, and remediation workflows without invoking the Codex CLI or changing course records when providers are switched.

## Product and usage boundary

The current app is a local, single-learner application. Codex OAuth is an experimental personal-use connector that relies on the Codex Responses backend and OAuth integration used by the Pi AI provider. It is not presented as a stable, generally supported OpenAI API. OpenAI’s public documentation describes ChatGPT sign-in within Codex and states that ChatGPT/Codex usage follows the ChatGPT plan, while API-key calls use API pricing; it does not document a general-purpose OAuth API for third-party applications. If this private backend, OAuth client, plan eligibility, or account access changes, the connector must fail clearly and leave learning data intact. Existing OpenAI API, Anthropic API-key, and Fireworks API-key providers remain supported as stable alternatives. [OpenAI Codex usage](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex), [ChatGPT and API billing](https://help.openai.com/en/articles/9039756-managing-billing-settings-on-the-chatgpt-web-and-api-platform)

No Codex CLI executable, shell command, or CLI-owned credential file is used. Codex OAuth credentials belong to this app’s own local credential store. The user authorizes through a browser and can disconnect locally from Settings. The UI and README must describe the connector as subject to change and distinguish subscription usage from API billing.

## Approved approach

Keep the existing Vercel AI SDK adapters for OpenAI API keys, Anthropic API keys, and Fireworks. Add a narrow Codex adapter based on Pi’s `openai-codex` provider, OAuth, and Responses implementation, with an app-owned boundary that normalizes generation to the current `streamText` / `generateText` contract. Use Pi AI's programmatic `createModels`, register `openaiCodexProvider()` with `models.setProvider()`, use provider `models.login`, OAuth interaction callbacks, and `CredentialStore`; this remains in-process Node library use, with no Pi CLI. Reuse the published Pi flow’s public OAuth client ID (`app_EMoamEEZ73f0CkXaXp7hrann`) and fixed browser redirect (`http://localhost:1455/auth/callback`); this is an explicit experimental dependency, not an app-specific OpenAI client registration or a claim that OpenAI supports third-party OAuth clients. The implementation review must verify current upstream values and integration behavior before coding. If that OAuth client stops working or its use becomes unsuitable, disable Codex OAuth with a clear status and retain the API-key providers; do not silently substitute an unregistered client or ask users for an API key while labeling it as subscription quota. Pin a verified Pi AI release and wrap its credential store with the app's file permissions and generation checks. The browser flow may run only if `localhost` resolves exclusively to one loopback address; set Pi's callback host to that same address. If name resolution is ambiguous or non-loopback, start directly in device-code mode. Pi's pinned public API does not reliably report local callback-listener bind failures, so keep browser login's manual-code stage and provide an explicit “Use device code instead” cancel-and-retry action; do not claim automatic port-conflict detection. Device flow is the explicit fallback and must honor provider polling intervals, slow-down responses, cancellation, and timeout. Attribute any vendored MIT source (vendoring is not preferred if the dependency API works). No unrelated LLM or course refactor is in scope; targeted deferral of generation-related state writes until a valid result exists is in scope to preserve course state on provider failure. [Pi OAuth source](https://github.com/earendil-works/pi/blob/main/packages/ai/src/auth/oauth/openai-codex.ts), [Pi Codex provider](https://github.com/earendil-works/pi/blob/main/packages/ai/src/providers/openai-codex.ts), [Pi programmatic auth/credential store](https://github.com/earendil-works/pi/blob/main/packages/ai/README.md), [Pi provider documentation](https://pi.dev/docs/latest/providers)

## Core invariants

1. **Course data is provider-neutral.** Provider/model/reasoning settings never appear as foreign keys or attributes on topics, modules, lessons, progress, quizzes, exams, reviews, artifacts, or saved chat messages. Changing settings does not update, delete, reorder, regenerate, or reset any existing course or learning record.
2. **A request is pinned to its start configuration.** At the start of each user-triggered LLM operation, resolve an immutable snapshot containing provider, model, reasoning effort, and the selected authentication mechanism. Pass that snapshot through every generation call in the operation. Saving a new provider affects only later operations. A running request/stream is not switched or transparently retried on another provider.
3. **Future content is naturally provider-dependent.** A later user-requested generation may have different wording or answers because it uses the selected model. It resumes from the same stored course IDs, lesson context, and chat history. Switching providers never automatically regenerates or rewrites material.
4. **No implicit fallback.** If the selected provider is disconnected, rate-limited, unavailable, or cannot serve the selected model/effort, report a typed error and preserve the selection and course state. The user may explicitly choose another ready provider.
5. **Secrets stay out of learning data.** Access tokens, refresh tokens, authorization codes, PKCE verifiers, and account identifiers are excluded from SQLite, HTTP responses, application logs, data exports/imports, and client storage. The OAuth authorization URL necessarily includes the transient state value; return it only to the Settings UI when its exact local Origin and API Host are allowlisted, for immediate navigation, keep the verifier and authoritative state server-side, and never persist or log the URL/state.

## Architecture and responsibilities

### Provider-neutral LLM configuration

Extend the LLM configuration resolver to return provider, model, reasoning effort, auth type, and readiness metadata. The migration default for existing API-key models with no reasoning option is the neutral `'none'` sentinel; only Codex models receive model-supported effort choices. Preserve `apiKeySet` as the status of an API-key provider for old UI/tests during migration; add a provider-neutral `ready` / `authStatus` for routing and onboarding. The resolver must return secrets only to server-side provider adapters. A single settings row remains the source of the active global generation preference; saving it is transactional. Selecting Codex while disconnected is allowed and reports not ready; generation remains gated on readiness. API-key providers continue reading keys from their current environment variables.

`requireLlmConfig()` (or its replacement) must check readiness according to the selected provider: non-empty environment key for existing providers, locally stored usable OAuth credentials for Codex. Provider availability is not the same as a successful remote request; stored OAuth can be marked connected while a later refresh/request discovers revocation or plan/model ineligibility.

### Codex authentication and credential storage

Add an OAuth manager around Pi AI's provider-owned login flow. The Settings UI calls local OAuth endpoints; because the development UI (`http://localhost:3201`) and API (`http://localhost:3200`) are cross-origin, enforce an exact allowlist of local UI `Origin` values plus expected local API `Host` values on start, status, manual-code, cancel, and disconnect endpoints despite permissive general CORS. The server invokes `models.login('openai-codex', 'oauth', interaction)` and implements `prompt`/`notify` without terminal I/O. Browser login is enabled only when `localhost` resolves to exactly one loopback address; set `PI_OAUTH_CALLBACK_HOST` to that same address before starting the login flow so the fixed `http://localhost:1455/auth/callback` redirect reaches Pi's listener. If resolution is ambiguous/non-loopback, start device-code login. Pi's pinned public API does not reliably report callback-listener bind failures, so keep browser login's manual-code stage and provide an explicit “Use device code instead” action that cancels and retries; do not claim automatic port-conflict detection. Show the authorization URL or device code only in the active Settings UI, do not log or persist it, and keep flow state/PKCE verifier server-side within Pi's flow. Let the provider implementation validate state/PKCE and exchange the authorization code; it owns its callback listener and success/error page. Device-code polling honors provider intervals/slow-down responses and expires after the provider's documented timeout. Cancelled, expired, failed, or replayed flows leave existing credentials and selected provider untouched.

Persist the minimum tokens and provider-required account metadata in a separate app-owned file under the current OS user’s private application-data directory, never in the repo, database, browser storage, or normal roadmap backup. Restrict directory/file permissions to the user (0700/0600 on POSIX and current-user-only ACLs on Windows), write atomically, and avoid following attacker-controlled paths. Implement Pi AI's `CredentialStore` interface over that file and use a cross-process lock (with bounded wait and stale-lock recovery) for every OAuth-flow start/commit, token refresh, account replacement, and disconnect. Persist a monotonically increasing OAuth-flow epoch in the credential-store metadata. Starting any browser/device flow increments the epoch under the lock and retains it after the flow ends; a flow may commit credentials only if its epoch still equals the persisted latest epoch. Run `models.login()` inside an async context carrying that epoch; the store's `modify()` rejects stale login writes. This makes the newest-started flow win across processes, even if an older flow completes later, and ensures a disconnect (which also increments the epoch) invalidates pending flows. Under the lock, refresh must re-read the latest file before using or replacing credentials and atomically replace it only if the credential generation still matches. Store an opaque credential-generation ID that changes on successful account replacement/disconnect but remains stable through token refresh. Each Codex operation captures this generation at start and may refresh/use only credentials from that same generation, so switching accounts mid-request can never cause the request to use the new account. Wrap the request's `CredentialStore.read()`/`modify()` in an async context carrying the captured generation; the store rejects reads or writes after account replacement/disconnect. Because `streamText()` returns a lazy stream that is consumed later, the adapter must re-enter the captured context for each iterator `next()` and `return()` call, not only while creating the stream. Test account disconnect/replacement after stream creation and before its first read; the store must reject it instead of using the replacement credential. Disconnect invalidates the generation under the same lock; a previously started HTTP stream may finish with the token already sent, while later calls from that operation fail rather than use a replacement account. A file-level disconnect means local removal; do not claim that it remotely revokes OpenAI’s authorization unless the protocol exposes and verifies a supported revocation operation.

Refresh access tokens before calls when needed, serialize concurrent refreshes (including persistence of rotated refresh tokens), and map expired/revoked credentials to a reconnectable error. Never return or log tokens, codes, or full Authorization headers. Treat account switching as replacing the app’s one active Codex identity only after a new OAuth flow succeeds; a failed login leaves the previous connection intact. Disconnect is explicit and must not clear provider-neutral learning data.

### Codex generation adapter

Use the Pi `openai-codex` model catalog and OAuth-backed Responses transport without invoking a CLI. Normalize stream events to text chunks compatible with the existing SSE route helper, and normalize non-streaming completion to `{ text, ... }` for existing JSON generation. Pass model and selected reasoning effort only when supported by the selected model metadata. Preserve system instructions, message order/roles, text content, abort signals where available, and existing response formats. Reject unsupported payload shapes or options deliberately rather than silently dropping instruction/context. Handle chunk boundaries, partial SSE frames, UTF-8 splits, `[DONE]`, provider error events, malformed streams, empty completions, cancellation, timeouts, 401/403, 404/model unavailable, 429, and network failure without leaking response bodies or credentials.

The current implementation is text-generation oriented. Tool execution, filesystem access, command execution, image input, and background tasks are out of scope. Never send tool declarations or grant Codex desktop/CLI permissions from this adapter.

### Settings API and UI

Expose Codex as a distinct provider ID (for example, `openai-codex`) so it cannot be confused with OpenAI API-key billing. Settings status reports provider, model, reasoning options, provider readiness, and sanitized auth status only. Add start OAuth, callback/completion, and local disconnect operations. Add the Codex model catalog/reasoning options through a server-owned allowlisted catalog; do not accept arbitrary model IDs or reasoning strings from clients. Existing providers and routes retain their current model lists and key configuration behavior.

Settings UI should provide Connect/Disconnect, account-neutral connection status, supported model selection, model-specific reasoning effort, and clear statuses for connecting, connected, reconnect required, disconnected, failed, and unavailable. Do not show secrets or identifiable account claims. The validation action stays local and side-effect-free (it reports configuration readiness, not a paid test generation). Onboarding gates on provider-neutral readiness, so a connected Codex provider works without any `.env` API key. Provider switching is a user preference; do not block selecting another configured provider just because Codex is disconnected.

### Persistence, migrations, and backup compatibility

Add a forward-only SQLite migration for a reasoning-effort preference with a safe default that preserves old installations. Keep the current single-row settings semantics and make writes atomic. Existing exports may include provider/model/reasoning preference but never OAuth credentials or auth metadata. Old backups that lack the new field must import with the migration default. Importing a backup containing Codex settings on a machine without local OAuth credentials keeps all courses intact, reports Codex as disconnected, and allows the learner to connect Codex or explicitly switch providers. Avoid accepting or restoring token-shaped fields from backup imports.

### Course flow and in-flight behavior

Every top-level route operation captures configuration once before its first model call and passes it into helpers; helpers must not resolve global settings again midway through the operation. Validate provider readiness before any generation-related database mutation. Defer progress/chunk transitions, user/assistant message persistence, quiz/retest/exam attempt creation, and curriculum replacement until the generated result is complete and validated; a provider/auth failure or malformed result must not strand a state transition or skip a lesson chunk. Existing successful endpoint semantics and explicit learner answer submissions remain intact. This matters for multi-call operations such as setup-question generation followed by curriculum generation and any route that streams/generates more than once. A new request after a user changes provider reads the new settings and receives the same course IDs and persisted lesson/chat context. A provider save does not touch learning tables. In-flight generation started before the change completes with its captured provider/model/effort; no automatic cancellation, provider mix, or fallback occurs. If an active stream fails, existing route error handling applies and no unrelated course/progress changes are made.

## Failure and recovery behavior

- OAuth cancelled, denied, expired, malformed, replayed, or callback port unavailable: show actionable status and offer explicit device-code retry; do not modify the previous valid account or settings.
- No credentials / refresh rejected / refresh service unavailable: return provider-specific errors; preserve course state and do not write pending generation-related state or attempts. Offer reconnect or explicit switch to a ready provider.
- User changes provider during a stream: finish under the original snapshot; subsequent requests use the new provider. Saved settings never retroactively alter the stream.
- Codex model removed, effort unsupported, or account lacks access: reject before writing generated learning data; retain preference unless user changes it, and explain the problem.
- Codex backend protocol changes, sends malformed SSE, or returns provider errors: terminate that request cleanly, keep already persisted course data, and do not switch providers or commit partial malformed JSON as a curriculum.
- Concurrent connect/disconnect/refresh operations across requests and app processes: serialize writes with a cross-process lock and generation check; only the most recently started successful OAuth flow may replace the stored credential; disconnect must invalidate older in-flight refreshes. A request pinned to an earlier generation may not pick up a replacement account.
- App restart, stale/missing credential file, restrictive filesystem, stale lock recovery, backup restore, old DB migration, and simultaneous app instances: provide deterministic recovery messages, preserve existing app startup behavior where possible, and never fall back to another account or provider silently.

## Test and acceptance requirements

Use deterministic unit and integration tests with mocked OAuth/network boundaries; do not require real ChatGPT credentials or make real quota-consuming calls in CI.

1. **Regression baseline:** Existing OpenAI, Anthropic, and Fireworks adapter, settings, onboarding, route, export/import, and frontend tests still pass.
2. **OAuth lifecycle/security:** PKCE/state validation, wrong/expired/replayed state, cancellation, concurrent starts, callback-port conflict, successful connection, failed reauth preserving existing credentials, refresh/rotation, refresh single-flight, logout/refresh race, permission failures, atomic file persistence, and secret redaction.
3. **Codex transport:** model and reasoning mapping, system/message preservation, streamed and non-streamed output, frame/chunk splits, UTF-8 splits, `[DONE]`, remote error events, malformed/empty responses, first-byte and idle timeout cancellation, abort, 401/403/404/429, and safe error mapping.
4. **Readiness/UI:** API-key readiness remains unchanged; connected Codex is ready without an API key; disconnected Codex is not ready; onboarding and settings display accurate states; unsupported model-effort pairs are rejected; status endpoints never return secrets.
5. **Data protection:** exports never contain OAuth values; import ignores/rejects token-shaped fields; pre-migration databases and backups without reasoning effort load with defaults; failed settings writes are atomic; OAuth disconnect leaves every learning table unchanged.
6. **Course-invariance acceptance test:** Seed a topic with modules, lessons, progress, messages, attempts, reviews, and artifacts. Snapshot all learning tables. Start a mocked streaming generation on provider A, switch settings to provider B before its stream completes, then complete it. Assert the original in-flight call used provider A and its captured model/effort, the next operation uses B, course IDs/order/progress/history/attempts remain unchanged except for the exact data the completed original route is designed to append, and no route silently changes provider mid-operation. For missing/disconnected config, upstream failures, and invalid generated output, assert no incomplete message/state/chunk/attempt writes and that curriculum regeneration retains the current draft. Repeat around a provider change between lesson chunks.
7. **Migration/build:** run backend and frontend test suites, production frontend build, and migration tests against a database created from the previous schema.

## Rollout and documentation

Ship Codex as an opt-in provider in Settings. Do not change the default provider or existing saved settings. Add concise README guidance covering local OAuth connect/disconnect, model/reasoning selection, the unofficial/private-backend dependency and possibility of breakage, personal-use boundary from the Pi integration guidance, separate ChatGPT and API billing, local token file location/permissions, and the supported fallback to OpenAI API key, Anthropic API key, or Fireworks. Document that switching provider preserves saved learning records while future generated text may vary.

## Explicit non-goals

- Running `codex`, `codex exec`, Pi CLI, or any other child process.
- Adding multi-user authentication, account profiles, cloud sync, or hosted token storage.
- Changing course schemas, progress logic, curricula, or historical content when provider settings change.
- Automatically falling back between providers, replaying user prompts under another account, or automatically regenerating a course.
- Tool use, coding-agent filesystem/terminal access, image inputs, or general Codex agent features.
- Replacing existing API-key integrations or switching them to subscription-based auth.
